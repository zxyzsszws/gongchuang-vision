## 1. 物理层

- UART **115200 - 8 - N - 1**
- 多字节字段一律 **little-endian**（int16 / uint16）

## 2. 帧格式（冻结）

```
AA 55 | len(1B) | seq(1B) | cmd(1B) | payload(N=len-7 B) | xor(1B) | 0D
```

| 字段 | 说明 |
|---|---|
| `AA 55` | 帧头，两字节定界 |
| `len` | **含头尾的总字节数** = 7 + payload 长度；固定开销 7 字节 |
| `seq` | 序号，见 §2.1 |
| `cmd` | 命令码，见 §3 |
| `payload` | N = len − 7 字节 |
| `xor` | 从 `len` 起、到 `payload` 末（即 len、seq、cmd、payload 全部）逐字节异或 |
| `0D` | 帧尾 |

流式解析：接收端实现为 `StreamDecoder.feed()`，抗粘包/断包；`len < 7` 或 `len > 128` 视为坏帧丢弃 → **单帧 payload 上限 121 字节**（本协议最大帧 TASK_PLAN 仅 12 字节，余量充足）。

### 2.1 seq 约定

- 视觉侧外发帧（TASK_PLAN/GOTO/CALIBRATE/PLACE/PICK/HEARTBEAT/ACK 回复等）seq 在 **1..255** 循环自增。
- **0 保留**给链路周期性自增上行帧：`POSE` 与 `DONE` 的 seq 恒为 0（视觉侧对 seq=0 的 POSE 不按 seq 去重，逐帧消费）。
- `ACK` 的有效信息在 payload（被确认帧的 seq），其自身 seq 无消费语义。

### 2.2 校验规则

xor 覆盖范围：`len..payload`（不含帧头 `AA 55`、不含 xor 自身与帧尾 `0D`）。任一字节不符（含帧尾非 `0D`）→ 整帧丢弃并计数。

## 3. 命令表

| 命令 | 码 | 方向 | payload 结构 | 说明 |
|---|---|---|---|---|
| HEARTBEAT | `0x10` | 双向（视觉周期发） | 空 | 500ms 周期；任一侧 2s 无来流 → SAFESTOP |
| TASK_PLAN | `0x11` | 视→控 | 12×1B：`b1色[3] b1位[3] b2色[3] b2位[3]` | 扫码结果，开赛只发一次。颜色 1-6，位置 1-3=环编号。**按批次分组排列**（见 §6.4） |
| GOTO | `0x12` | 视→控 | `x,y:int16(mm) heading:int16(0.1°)` | 请求导航（绝对坐标）。x/y = **FieldMap 数字环心**：NAV1/NAV2 目标取 TASK_PLAN 对应批次放置位置首位编号匹配的环心，无匹配环回退原点；RETURN 回起点 `(0,0)`。heading 当前恒发 0 |
| CALIBRATE | `0x13` | 视→控 | `dx,dy:int16(mm) dhead:int16(0.1°)` | **修正量**（非绝对坐标），主控叠加到其推算位姿 |
| PLACE | `0x14` | 视→控 | `id:1B fine_x,fine_y:int16(mm)` | 放置请求 + 视觉微调量。当前 FSM 第一字节填**物料颜色号**（见 §6.5） |
| PICK | `0x15` | 视→控 | `color:1B off_x,off_y:int16(mm)` | 取料请求 + 相对偏移。协议已定义，**当前 FSM 未外发**（预留，见 §6.6） |
| ACK/NAK | `0x16` | 双向 | `被确认帧 seq:1B` | 100ms 未 ACK 重发，3 次失败 → SAFESTOP |
| POSE | `0x20` | 控→视 | `x,y:int16(mm) heading:int16(0.1°) odom:uint16(m)` | 10Hz 主动上报，校准输入；seq=0 |
| STATE | `0x21` | 控→视 | `state:1B` | 主控状态；视觉侧当前仅收帧记录，FSM 推进只依赖 DONE |
| DONE | `0x22` | 控→视 | `task_id:1B` | 单动作完成事件，FSM 状态推进依据；seq=0 |

设计要点：校准走增量、主控保留推算主权；场地原点=扫码区角点，双方共用 FieldMap（单位 mm，0.1°）。

## 4. 字节级示例（`encode()` 实际输出）

以下 hex 全部由视觉侧实现真实运行生成，电控组可直接用作收发单测的黄金样例。
复现命令（仓库根目录）：

```bash
python -c "from src.core.protocol import Frame, encode, CMD_TASK_PLAN; print(encode(Frame(1, CMD_TASK_PLAN, bytes((4,5,2,3,2,1,2,5,4,3,1,2)))).hex(' '))"
```

### TASK_PLAN（seq=1，对应二维码 `452+321+254+312`）

第一批颜色 4,5,2｜第一批位置 3,2,1｜第二批颜色 2,5,4｜第二批位置 3,1,2（payload 12 字节，总长 12+7=19=`0x13`）：

```
aa 55 13 01 11 04 05 02 03 02 01 02 05 04 03 01 02 03 0d
```

### GOTO（seq=2，x=1200mm，y=300mm，heading=45.0°→450）

```
aa 55 0d 02 12 b0 04 2c 01 c2 01 47 0d
```

（`b0 04`=1200 LE，`2c 01`=300 LE，`c2 01`=450 LE）

### GOTO 实例（seq=8：NAV 目标 = FieldMap 3 号环心 (1200,900)，heading 恒发 0）

视觉侧当前真实外发的导航帧形态——目标点由 TASK_PLAN 批次位置首位匹配环心得出：

```
aa 55 0d 08 12 b0 04 84 03 00 00 24 0d
```

（`b0 04`=1200 LE，`84 03`=900 LE，`00 00`=0；`encode()` 实际输出）

### CALIBRATE（seq=3，dx=−12mm，dy=45mm，dhead=8.3°→83）

```
aa 55 0d 03 13 f4 ff 2d 00 53 00 68 0d
```

（`f4 ff`=−12 补码 LE，`2d 00`=45，`53 00`=83）

### PLACE（seq=4，颜色 1，微调 fine_x=−15mm，fine_y=30mm）

```
aa 55 0c 04 14 01 f1 ff 1e 00 0d 0d
```

（注意此帧 xor 恰为 `0d`，与帧尾 `0d` 相邻出现两次属正常）

### PICK（seq=5，颜色 2，偏移 10mm，−20mm）

```
aa 55 0c 05 15 02 0a 00 ec ff 07 0d
```

### HEARTBEAT（seq=6，空 payload，总长=7）

```
aa 55 07 06 10 11 0d
```

### ACK（确认 seq=2 的帧）

```
aa 55 08 01 16 02 1d 0d
```

### POSE 上行（seq=0，x=1520mm，y=300mm，heading=−123.4°→−1234，odom=1m）

```
aa 55 0f 00 20 f0 05 2c 01 2e fb 01 00 23 0d
```

（`2e fb`=−1234 补码 LE，`01 00`=1，odom uint16）

### DONE 上行（seq=0，task_id=7）

```
aa 55 08 00 22 07 2d 0d
```

### STATE 上行（state=3）

```
aa 55 08 00 21 03 2a 0d
```

### 边界示例：GOTO x=32767（int16 正向饱和值）、y=−32768、heading=−18000（−180.0°）

```
aa 55 0d 07 12 ff 7f 00 80 b0 b9 11 0d
```

## 5. 时序与容错参数（冻结项）

| 参数 | 值 | 来源 |
|---|---|---|
| HEARTBEAT 周期 | 500ms | `timing.heartbeat_ms` |
| 无来流超时 | 2s → SAFESTOP | `timing.heartbeat_timeout_s` |
| ACK 超时 | 100ms 重发 | `timing.ack_timeout_ms` |
| ACK 重试上限 | 3 次失败 → SAFESTOP | `timing.ack_retry` |
| POSE 上报频率 | 10Hz | `MockMcu(pose_hz=10)` 同模型 |

心跳帧不占用 ACK 待确认槽位（发送方不依赖心跳的 ACK）；接收侧对任何帧（含心跳）均可回 ACK。发送侧**控制帧串行化**：上一条控制帧（TASK_PLAN/GOTO/CALIBRATE/PLACE）的 ACK 未解决（含重发预算未耗尽）之前不会发出下一条控制帧，预算耗尽仍无 ACK 则记 ACK_TIMEOUT 并 SAFESTOP；NAV/PLACE 超时重发每次重开完整超时窗口（RETRY(n) 语义，缺省 8s × 2 次重发）。

## 6. 已知限制与实现裁决（必读）

以下为实现代码的真实行为，与规格文字有差异或规格未覆盖，**以代码为准**并共同冻结：

### 6.1 坐标 int16 量程与「饱和不回绕」

x/y 为 int16、单位 mm → 单向表示范围 **−32768 … +32767 mm（约 ±32.7 m）**，远超赛场尺寸，正常使用不会触界。
超界值处理：**饱和钳位（clamp），不是回绕（wrap）**——视觉侧打包前用 `_i16()`（`max(−32768, min(32767, v))`），MockMcu 同样 `_clamp_i16()` 并在钳位时计数告警。主控侧解析无需处理回绕歧义。

### 6.2 航向 0.1° 的回绕约定

heading 为 int16、单位 0.1°。有效角度先回绕到有符号区间 **`[-18000, 18000)`（即 [−180.0°, +180.0°)）** 再打包，公式：

```
h01 = ((h01_raw + 18000) % 36000) - 18000     # h01_raw 为 0.1° 单位的任意整数
```

原因：Python `%` 恒非负，负净航向会被映射到 `[1, 35999]`，≥32768 时 `struct '<h'` 直接抛异常——已实现并测试固化（commit `725811c`）。CALIBRATE 的 dhead 同理：视觉侧取先归一到 ±180° 的差值再 ×10。**经 §6.1 回绕后仍超 ±32767 的值不存在（回绕区间是 int16 子集），故 heading 不会走饱和路径。**

### 6.3 odom 为 uint16 米

POSE 的里程字段 0..65535 m，超出后按 `& 0xFFFF` 回绕（赛场里程 <100m，无实际影响）。

### 6.4 TASK_PLAN 字节序裁决

规格表曾写作 `batch1[3] batch2[3] pos1 pos2 posS`，**实现按批次分组**：`b1色(3) | b1位(3) | b2色(3) | b2位(3)` 共 12 字节（与二维码 4 组数字 `452+321+254+312` 的字面顺序一一对应，便于对账）。以本文与 §4 黄金样例为准。

### 6.5 PLACE 第一字节语义

规格写作 `ring_id`，当前 FSM 外发时填**该批次首个物料颜色号**（PLACE1=`batch1_colors[0]`、PLACE2=`batch2_colors[0]`，1-6，与二维码颜色组首位一致）。fine_x/fine_y 为视觉微调量字段，**当前恒发 0**（逐件精细放置偏移属 Phase-4）。放置目标环编号已含在 TASK_PLAN 的位置字节中。若电控组需要 PLACE 携带独立 ring_id，请在联调前提出，改 `_s_PLACE1/2` 一处即可。

### 6.6 PICK / STATE 当前未使用

`PICK(0x15)` 帧格式已定义、MockMcu 已按「动作命令 → 延迟 1 tick 回 DONE」处理，但当前 FSM 状态序列中没有取料动作，不会外发；`STATE(0x21)` 视觉侧收到后仅记录。两者为联调预留，电控组可按本表实现亦可暂缓。

### 6.7 视觉侧坐标系与校准输入口径（电控组必读）

校准帧 `CALIBRATE` 下发的 `dx,dy,dhead` 是**场地坐标系下的绝对修正量**，来源：
「三色环在图像中的位置 → 经相机安装外参换到车体毫米 → 用**主控最近上报的位姿**换到场地毫米」，再与场地图理论环心比较。因此：

- 视觉侧观测的坐标系与主控上报位姿**必须同一套**（原点=扫码区角点，mm，右/前为 +x/+y）。若主控坐标系定义与此不同，校准量会整体错位——联调第一件事就是对齐坐标系与单位。
- 校准量依赖 `POSE` 上报的时效性：视觉用最近一帧 POSE 位姿做换算，10Hz 上报下延迟 ≤100ms，车静止于三色环前时无影响；若主控在校准窗口内仍在移动，请先停稳再让视觉采样。
- 视觉侧在**未完成相机外参标定**时会拒绝进入 live 模式（退出码 2），不会发出未校准的修正量。

前言

本协议定义「视觉单元（Jetson）↔ 机器人主控」之间的串口通信，适用于 2027 年工程创新大赛智能搬运赛项。

分工的总原则只有一条：

- **视觉单元只做测量**：它把「自己在场地里的位置和朝向」「转盘上三件物料怎么转」以及「机械臂该怎么动才能到达目标点」量出来发给机器人主控，不规划行驶路径、不判断动作是否完成。
- **机器人主控只做执行**：它根据赛前量好的场地图自己规划行驶路径、自己控制底盘与升降，自己决定何时取料与放料。

因此在正常情况下，机器人主控完全不需要向视觉单元索取任何位置信息；只有当里程推算累积了误差、需要视觉单元给出一次准确的位姿来纠正时，才使用视觉单元上报的数据。

视觉单元也不主动下发任何动作指令。唯一由电控主动发起、视觉作答的交互是**机械臂目标解算**：电控把「臂伸多长、现在转多少度」告诉视觉，视觉回「车该沿自身 x 挪多少、臂该转多少度」。相机高度不必上报——参考靶的外圈直径是固定值，视觉用它在画面里的像素尺寸就能反算出尺度。

帧格式、帧头定义、命令码 ID 一览的编排方式与校验算法均参照《RoboMaster 2027 机甲大师高校系列赛通信协议 V1.0.0》；命令码与数据段内容为本赛项自行定义。

# 1 串口协议

## 1.1 串口协议格式

通信方式为串口的部分，性质如下：8 位数据位，1 位停止位，无硬件流控，无校验位。详细信息见以下表格：

表 1-1 波特率

| 物理接口 | 波特率 |
|---|---|
| 视觉单元←→机器人主控 | 115200 |

表 1-2 通信协议格式

| frame_header | cmd_id | data | frame_tail |
|---|---|---|---|
| 5-byte | 2-byte | n-byte | 2-byte，CRC16，整包校验 |

表 1-3 frame_header 格式

| SOF | data_length | seq | CRC8 |
|---|---|---|---|
| 1-byte | 2-byte | 1-byte | 1-byte |

表 1-4 帧头详细定义

| 域 | 偏移位置 | 大小（字节） | 详细描述 |
|---|---|---|---|
| SOF | 0 | 1 | 数据帧起始字节，固定值为 0xA5 |
| data_length | 1 | 2 | 数据帧中 data 的长度加 2（含 cmd_id 的 2 字节），小端 |
| seq | 3 | 1 | 包序号 |
| CRC8 | 4 | 1 | 帧头 CRC8 校验，覆盖偏移 0~3 共 4 字节 |

说明：

- `data_length` 的取值范围为 2~1026。接收方若读到该范围之外的值，判定为坏帧。
- `frame_tail` 为 CRC16，覆盖范围为 `frame_header`（含 CRC8）+ `cmd_id` + `data`，即**除 `frame_tail` 自身外的全部字节**，也就是表 1-2 所称「整包校验」。
- 一帧的总字节数 = 5 + `data_length` + 2。
- 多字节字段（`data_length`、`cmd_id`、CRC16 以及所有 data 内的多字节量）一律为**小端**。
- 接收方必须实现流式解析，抗粘包与断包；帧头或 data 未收全时保留缓冲等待下一批数据，不得报错丢弃。
- 双方各自的 `seq` 单调递增，从 1 递增到 255 后回到 1，0 保留不使用。**两侧的 seq 空间互相独立**，视觉发出的 seq 与电控发出的 seq 互不干涉，配对只靠应答帧里的 `ack_seq` 与解算帧里的 `echo_seq`。
- **重发时 seq 不变。** 这一点与「seq 单调递增」并不冲突：单调递增描述的是**新帧**，重发的是同一帧、内容逐字节相同，接收方据此识别重复。详见 1.7 节。

## 1.2 命令码 ID 一览

表 1-5 命令码 ID 一览

| 命令码 | 数据段长度 | 说明 | 发送方/接收方 |
|---|---|---|---|
| 0x0002 | 16 | 任务计划，扫码成功后触发发送，每场比赛发送一次 | 视觉单元→机器人主控 |
| 0x0003 | 9 | 车身在场地中的位姿，能看见当前区域三个参考靶时以 20Hz 发送 | 视觉单元→机器人主控 |
| 0x0004 | 16 | 转盘上三件物料的转动模型，能看见转盘时以 20Hz 发送 | 视觉单元→机器人主控 |
| 0x0005 | 1 | 去向提示，机器人主控每次改变行驶目标区域时发送 | 机器人主控→视觉单元 |
| 0x0006 | 5 | 臂状态，电控请求解算时发送，发后必须保持静止 | 机器人主控→视觉单元 |
| 0x0007 | 2 | 应答，收到并执行完后回送；是任务计划的应答，也是解算的 done | 双向 |
| 0x0008 | 10 | 臂解算结果，是对 0x0006 的应答 | 视觉单元→机器人主控 |

命令码分段约定：`0x00xx` 为视觉单元发往机器人主控，`0x02xx` 保留给机器人主控发往视觉单元的方向（本版本暂不使用）。

**本版本没有心跳。** 周期性测量帧（位姿 20Hz、转盘 20Hz）本身就是链路活跃的证据，再加一层心跳是重复的。真正需要确认对方收到的只有两处往返（任务计划、臂解算），它们各有应答超时，超时重发、重试超限就安全停止——链路死掉一定会在这两处之一暴露出来。

反过来说，**不能靠「多久没收到任何来帧」判断断链**：电控是事件驱动的，停着作业时可能十几秒不发一帧，那是正常状态。把静默当断链只能得到误报。

本版本**不使用**下列命令，接收方遇到应静默丢弃并计数，不得视为错误：

| 命令码 | 原含义 | 不再使用的原因 |
|---|---|---|
| 0x0001 | 心跳 | 周期性测量帧已能证明链路活跃；且静默被误当断链 |
| 0x0201 | 主控上报场地位置 | 位姿由视觉单元自行测算，不需要主控提供 |
| 0x0202 | 主控状态 | 视觉单元不推进流程，不需要知道主控状态 |
| 0x0203 | 单动作完成事件 | 视觉单元不推进流程；动作完成只通过 0x0007 的 done 体现 |

## 1.3 数据段详细定义

### 表 1-6 0x0002

| 字节偏移量 | 大小 | 说明 |
|---|---|---|
| 0 | 3 | 二维码第 1 组：第一批 3 件物料的颜色与搬运顺序，每字节 1~6，按搬运先后排列 |
| 3 | 3 | 二维码第 2 组：第一批 3 件物料在粗加工区与暂存区的放置位置，每字节 1~3。两处通用同一个靶号 |
| 6 | 3 | 二维码第 3 组：第二批 3 件物料的颜色与搬运顺序，每字节 1~6 |
| 9 | 3 | 二维码第 4 组：第二批 3 件物料在**粗加工区**的放置位置，每字节 1~3 |
| 12 | 3 | 第二批 3 件物料在**暂存区**的放置位置，每字节 1~3。由视觉单元按颜色与第一批配对算得，见下 |
| 15 | 1 | 校验字节，见下表 |

```
typedef __packed struct
{
  uint8_t batch1_color[3];
  uint8_t batch1_ring[3];
  uint8_t batch2_color[3];
  uint8_t batch2_ring_rough[3];
  uint8_t batch2_ring_staging[3];
  uint8_t status;
}task_plan_t;
```

校验字节：

| 位 | 含义 |
|---|---|
| bit 0 | 两批颜色集合能配对（1 为能，0 为不能） |
| bit 1 | 保留，固定为 0 |
| bit 2 | 第 2 组是 1~3 的一个排列（1 为是，0 为有重复靶号） |
| bit 3 | 第 4 组是 1~3 的一个排列（1 为是，0 为有重复靶号） |
| bit 4~6 | 保留，固定为 0 |
| bit 7 | 整帧是否可用（1 为可用，0 为不可用，此时不得按本帧规划路径） |

对应关系（必须严格遵守，不得按颜色查表）：

1. 第 1 组第 i 位数字是第一批第 i 件物料的颜色，第 2 组第 i 位数字是它要去的靶号。
2. 第 3 组第 i 位数字是第二批第 i 件物料的颜色，第 4 组第 i 位数字是它在**粗加工区**要去的靶号。
3. 第 12~14 字节第 i 位数字是第二批第 i 件物料在**暂存区**要去的靶号。
4. 提取规则：第 12~14 字节由视觉单元计算，算法为「在第一批中查找与第二批第 i 件颜色相同的物料，取其第 2 组靶号」。由于同一批内颜色互不相同，该查找结果唯一。

示例：二维码 `452+321+254+312`

| 批次 | 件序 | 颜色 | 粗加工区靶 | 暂存区靶 |
|---|---|---|---|---|
| 第一批 | 1 | 4 | 3 | 3 |
| 第一批 | 2 | 5 | 2 | 2 |
| 第一批 | 3 | 2 | 1 | 1 |
| 第二批 | 1 | 2 | 3 | 1 |
| 第二批 | 2 | 5 | 1 | 2 |
| 第二批 | 3 | 4 | 2 | 3 |

第二批在暂存区必须码垛在第一批之上，且上下两层颜色一致。上表中第二批第 1 件颜色为 2，第一批颜色为 2 的物料在 1 号靶，故其暂存区靶号为 1，码垛在第一批第 3 件之上。

视觉单元在发送本帧前完成三项自检，任一不通过则**不发送本帧**，继续扫码：

1. 两批颜色集合能按上述规则一一配对；
2. 第 2 组是 1、2、3 的一个排列；
3. 第 4 组是 1、2、3 的一个排列。

本帧是视觉单元发给电控的**唯一需要应答**的帧。电控收到后回 `0x0007`；视觉单元未收到则重发原帧。

### 表 1-7 0x0003

| 字节偏移量 | 大小 | 说明 |
|---|---|---|
| 0 | 2 | 机械臂底座中心在地面的投影点，场地坐标系 x 坐标，单位：mm，有符号 |
| 2 | 2 | 机械臂底座中心在地面的投影点，场地坐标系 y 坐标，单位：mm，有符号 |
| 4 | 2 | 车头朝向，单位：0.1°，有符号，取值范围 −1800~1800，俯视逆时针为正 |
| 6 | 1 | 拟合残差，单位：0.5mm，无符号，超过 127 时按 127 发送 |
| 7 | 1 | 质量字节，见下表 |
| 8 | 1 | 本帧使用的参考靶组：1 为粗加工区，2 为暂存区 |

```
typedef __packed struct
{
  int16_t pos_x;
  int16_t pos_y;
  int16_t heading;
  uint8_t residual;
  uint8_t quality;
  uint8_t region;
}robot_pose_t;
```

质量字节：

| 位 | 含义 |
|---|---|
| bit 0~1 | 本次参与解算的靶数：1、2、3 |
| bit 2~3 | 靶编号来源：0 为读到靶心数字，1 为按入场方向约定推定，2 为与任务计划交叉核对，3 为无法区分 |
| bit 4 | 尺度来源：0 为使用赛前标定值，1 为由三个靶的间距当场自估 |
| bit 5~6 | 质量等级：0 差，1 中，2 好，3 优 |
| bit 7 | 本帧是否可用（1 为可用） |

机器人主控的使用规则：

- `quality` 的 bit 7 为 0 时整帧丢弃，继续使用自身里程推算。
- `quality` 的 bit 5~6 为「好」或「优」时，可同时采用位置与朝向。
- `quality` 的 bit 5~6 为「中」或「差」时，仅采用位置，不使用朝向。
- `residual` 用于判断本帧是否可信，不做强制门限，由机器人主控自行决定。

本帧是**周期测量帧，不应答**。

| 字节偏移量 | 大小 | 说明 |
|---|---|---|
| 0 | 2 | 转盘圆心在车身坐标系下的 x 坐标，单位：mm，有符号 |
| 2 | 2 | 转盘圆心在车身坐标系下的 y 坐标，单位：mm，有符号 |
| 4 | 2 | 工位回转半径，单位：mm，无符号 |
| 6 | 2 | 0 号工位当前角度，单位：0.1°，有符号，取值 −1800~1800，0 为车头方向，俯视逆时针为正 |
| 8 | 2 | 转动角速度，单位：0.1°/s，有符号，俯视逆时针为正 |
| 10 | 1 | 工位数量，固定为 3 |
| 11 | 1 | 状态字节，见下表 |
| 12 | 1 | 0 号工位的物料颜色，1~6，0 表示空位 |
| 13 | 1 | 1 号工位的物料颜色，1~6，0 表示空位 |
| 14 | 1 | 2 号工位的物料颜色，1~6，0 表示空位 |

```
typedef __packed struct
{
  int16_t center_x;
  int16_t center_y;
  uint16_t radius;
  int16_t angle0;
  int16_t omega;
  uint8_t station_count;

  uint8_t color[3];
  uint8_t reserved;

```

状态字节：

| 位 | 含义 |
|---|---|
| bit 0 | 转盘是否在转（1 为在转） |
| bit 1 | 三个工位是否全部识别到（1 为全部识别） |
| bit 2 | 角度是否已锁定，即连续多帧结果一致（1 为已锁定） |
| bit 3 | 三件物料的颜色是否全部可靠（1 为可靠） |
| bit 4~6 | 保留，固定为 0 |
| bit 7 | 本帧是否可用（1 为可用） |

工位角度约定：0 号工位位于 `angle0`，1 号工位位于 `angle0 + 1200`（即 120.0°），2 号工位位于 `angle0 + 2400`（即 240.0°）。角度均按 3600（即 360.0°）取模归一。

机器人主控的使用规则：

- 物料位置随时间变化，**不得**把 `angle0` 当作物料的静态位置使用。
- 需要伸向某颜色物料时，先在 `color[0..2]` 中查到该颜色的工位序号 k，得到该工位当前角度 `angle0 + 1200·k`，再按下式推算伸出耗时 t 之后该物料的角度：

```
angle_at_t = angle0 + 1200·k + omega·t     （结果按 3600 取模）
```

- 由于转盘周期为 6~10 秒，在 6 秒/转时工位角度变化率为 600（即 60.0°/s）。机械臂伸出若耗时 1 秒，物料将转动 60°，必须按上式补偿，不得直接使用 `angle0`。

本帧使用**车身坐标系**而非场地坐标系，原因见 1.5 节：原料区不存在参考靶，视觉单元在该处没有场地坐标可依。

本帧是**周期测量帧，不应答**。

### 表 1-9 0x0005

| 字节偏移量 | 大小 | 说明 |
|---|---|---|
| 0 | 1 | 机器人主控当前的行驶目标区域：1 为原料区，2 为粗加工区，3 为暂存区，4 为起点 |

```
typedef __packed struct
{
  uint8_t region;
}region_hint_t;
```

本帧是机器人主控发往视觉单元的**单向提示**，不是位置信息，只说明「我接下来要去哪个区域」，用于让视觉单元在粗加工区与暂存区这两组结构完全相同的参考靶之间做出选择。

它不是「唯一」的下行帧（V2.1.0 起还有 0x0006 臂状态），但仍是唯一的**区域**提示。

发送规则：

- 仅在目标区域发生改变时发送一次，不需要周期重发，**不需要应答**。
- 视觉单元收到后立即切换到对应的靶组，并在该组靶离开画面后停止发送 `0x0003`。
- 视觉单元若长时间未收到本帧，沿用上一次的取值，不得因此停止工作。
- 视觉单元在每一帧 `0x0003` 的第 8 字节回带当前使用的区域码，机器人主控可据此核对。

### 表 1-10 0x0006

| 字节偏移量 | 大小 | 说明 |
|---|---|---|
| 0 | 2 | 机械臂水平伸出长度 l，单位：mm，无符号 |
| 2 | 2 | 臂当前 yaw α，单位：0.1°，有符号，取值 −1800~1800，从 +x 量起、向 +y 为正 |
| 4 | 1 | 目标编号，0 表示不指定（画面里只有一个候选目标时用 0） |

```
typedef __packed struct
{
  uint16_t arm_length;
  int16_t arm_yaw;
  uint8_t target_id;
}arm_state_t;
```

这一帧是电控主动索取解算的请求。相机装在机械臂末端且正对地面，`l` 与 `α` 给出转轴到相机的平移与旋转，像素到毫米的**尺度则由视觉自己从画面里量出来**：参考靶的外圈直径是固定值，测它的像素直径即可反算 mm/px。

**为什么不要求电控上报相机高度。** 高度在这套算法里唯一的用途就是给出尺度，而尺度已经能从已知直径的靶上直接量到——让电控再报一个高度属于重复约束，且一旦电控报的高度与实际不符（升降没走到位、编码器零位偏），视觉会按错的尺度算出一个看起来正常、实际差一截的解，反而不如不报。少一个字段也少一处双方对不齐的风险：数据段只有 5 字节。

发送规则：

- **发出本帧后，电控必须在收到 0x0008 之前保持静止**（底盘不动、臂不转、升降不调）。理由见 1.6 节：视觉按「当前姿态」解算，若电控在等结果期间动了，解出的 d 与 α 就对应一个已经不适用的姿态；升降动了则会改变画面的尺度。
- 本帧的应答是 `0x0008`，**不另回 `0x0007`**。业务帧即应答，避免同一个请求有两种等法。
- 未在超时内收到 `0x0008` 时，重发**原帧（seq 不变）**，最多 3 次。

### 表 1-11 0x0007

| 字节偏移量 | 大小 | 说明 |
|---|---|---|
| 0 | 1 | 被确认帧的 seq |
| 1 | 1 | 结果字节，见下表 |

```
typedef __packed struct
{
  uint8_t ack_seq;
  uint8_t result;
}ack_t;
```

结果字节：

| 取值 | 含义 | 说明 |
|---|---|---|
| 0 | 成功 | 收到并已执行完 |
| 1 | 重复请求 | 该请求此前已执行过，本次不再重复执行，只补一次应答 |
| 2 | 失败 | 收到但无法执行（数据不合法、当前状态不允许等） |
| 3~255 | 保留 | 收到按失败处理并记录 |

本帧承担两种语义，靠 `ack_seq` 指向哪一帧来区分：

1. **任务计划的应答**：`ack_seq` 等于 0x0002 的 seq。
2. **臂解算的 done**：`ack_seq` 等于 0x0008 的 seq，且在两处动作都**执行完**之后才发。

只有这两类帧需要应答。位姿 0x0003、转盘 0x0004、去向提示 0x0005、臂状态 0x0006 一律不应答——它们或是周期测量帧，或已有业务帧作应答。若每帧都回一个应答，链路上有一半是纯应答帧，而且视觉无法判断「我该等哪一个」。

### 表 1-12 0x0008

| 字节偏移量 | 大小 | 说明 |
|---|---|---|
| 0 | 2 | 车沿自身 x 轴要移动的量 d，单位：mm，有符号。正为前进，负为后退 |
| 2 | 2 | 臂应转到的 yaw α，单位：0.1°，有符号，从 +x 量起、向 +y 为正 |
| 4 | 1 | 状态字节，见下表 |
| 5 | 1 | 回带值：本次解算对应的 0x0006 的 seq |
| 6 | 2 | 测得的目标点在电机坐标系下的 x 坐标，单位：mm，有符号 |
| 8 | 2 | 测得的目标点在电机坐标系下的 y 坐标，单位：mm，有符号 |

```
typedef __packed struct
{
  int16_t shift_x;
  int16_t arm_yaw;
  uint8_t status;
  uint8_t echo_seq;
  int16_t target_x;
  int16_t target_y;
}arm_solution_t;
```

状态字节：

| 位 | 含义 |
|---|---|
| bit 0~1 | 解算结果：0 成功，1 横向够不着，2 画面里没测到目标，3 保留 |
| bit 2 | 告警：\|α\| > 90°，臂会扫过车身 |
| bit 3 | 保留，固定为 0 |
| bit 4~5 | 质量等级：0 差，1 中，2 好，3 优 |
| bit 6 | 保留，固定为 0 |
| bit 7 | 本帧是否可用（1 为可用）。只有 bit 0~1 为「成功」时才置起 |

机器人主控的使用规则：

- `status` 的 bit 7 为 0 时**不得执行**，按结果码处理：
  - 结果为 1（横向够不着）：目标超出行程，电控自行决定是否挪车后重新请求；
  - 结果为 2（没测到目标）：换个观察姿态或调整车的位置后重新请求，不要沿用上一次的结果。
- `status` 的 bit 7 为 1 时，先沿自身 x 轴移动 `shift_x`，再把臂转到 `arm_yaw`。两件的先后顺序见 1.6 节。
- `target_x` / `target_y` 是视觉实测的目标位置，仅供诊断与二次规划，正常执行只需要 `shift_x` 与 `arm_yaw`。
- `echo_seq` 必须与电控发出的 0x0006 的 seq 相同。电控应据此丢弃过期的解算结果。

本帧的应答是 `0x0007`（`ack_seq` 等于本帧 seq），且在动作执行完之后才发。

表 1-13 全流程职责划分

| 步骤 | 机器人主控 | 视觉单元 |

| 1 扫码 | 等待 | 读二维码，自检，发 `0x0002` |
| 2 去原料区 | 按自身里程推算行驶 | 无参考靶，不发位姿 |

| 7 取回 | 原地重新取起所放物料 | 持续发 `0x0003` |

本流程共两趟，物料不换：

- 第一趟：原料区取第一批 3 件 → 粗加工区放到第 2 组靶号 → 原地取回 → 暂存区放到第 2 组靶号（第一层）
- 第二趟：回原料区取第二批 3 件 → 粗加工区放到第 4 组靶号 → 原地取回 → 暂存区按颜色配到对应靶号（码垛在第一批之上）

表 1-14 视觉单元的测量服务模型

| 条件 | 视觉单元的行为 |
|---|---|
| 当前区域的三个参考靶全部在画面内 | 每 50ms 发送一帧 `0x0003` |
| 当前区域的参考靶未能全部在画面内 | 停发 `0x0003`，不发送降级的或不完整的结果 |
| 转盘与三件物料在画面内 | 每 50ms 发送一帧 `0x0004` |
| 收到 `0x0006` 臂状态 | 一个主循环内回 `0x0008`（不等到下一个上报周期） |
| 以上条件都不满足 | 不发任何帧 |

关键性质：**精度只会在看不见参考靶的路段上变差；而在需要对准靶心放料的时刻，车辆必然位于能看见参考靶的位置，因此那一刻的位姿始终是准确的。** 两趟之间的里程误差会在到达下一个区域时被一次性全部清除，不会累积到放料动作。

为什么必须同时看见三个参考靶：

- 单个靶由多圈同心圆组成，关于自身中心旋转对称，仅凭一个靶只能得到 2 个测量量（靶心在车身坐标系下的 x、y），而未知量为 3 个（车身位置 x、y 与朝向），缺少的正是朝向。沿以靶心为圆心、以距离为半径的圆周行走一圈，观测结果完全相同。
- 三个靶心连成一条直线，该直线在场地坐标系下的方向是已知的，量出它在图像中的方向即可解出朝向。三个靶还提供一组冗余测量，可用于交叉检查是否认错靶。
- 因此视觉单元在只看见 1 个或 2 个靶时不发送 `0x0003`，仅在三个靶全部可见时发送。

为什么 `0x0004` 使用车身坐标系：原料区不存在参考靶，视觉单元在该处没有场地坐标可依。车身坐标系下的相对距离对车辆停位偏差天然不敏感，停偏 50mm 不改变「物料离车多远」这一测量结果。

## 1.6 机械臂目标解算

### 一、电机坐标系

解算使用的不是场地坐标系，而是**电机坐标系**，原点在**车身右侧边的中点**，也就是臂的转轴：

- +x 沿车头方向；
- +y 指向车身外侧（俯视图里的画面右方）；
- 车身本体落在 y < 0 一侧，x ∈ [−车长/2, +车长/2]；
- 单位一律为 mm。

臂的水平伸出长度 l 在比赛中固定死（不作为一个可调自由度），所以臂末端距转轴恒为 l。臂 yaw α 从 +x 量起、向 +y 为正，末端位置就是：

```
末端 = (l·cos α, l·sin α)
```

### 一之二、尺度从哪来

`l` 与 `α` 只能定出「相机相对转轴在哪、朝哪」，还差一项**像素到毫米的换算比例**。这一项视觉自己量：参考靶的外圈直径是固定值（赛前量一次，写进配置），量出它在画面里的像素直径，`mm/px = 外圈直径 ÷ 像素直径`。

这样做比让电控上报相机高度可靠：高度算尺度的前提是「相机光轴严格垂直地面、镜头无畸变、高度已知且准确」，三项任一不成立都会系统性偏；而用靶本身量，尺度与被测物在同一张画面里，畸变与倾斜的影响大部分相消。台面上没有靶时（例如对着转盘取料），就沿用标定时的固定 `scale_mm_per_px`——那种场合对绝对精度的要求本来也低一档。

### 二、解算公式

要让末端落在目标点 (x, y) 上：

```
α = asin(y / l)          横向位置只能靠臂转出来
d = x − l·cos α          前后位置靠车沿自身 x 挪
```

d 是**相对当前位置**的移动量：正为前进，负为后退。视觉单元每次都从头算，不做跨帧累积；电控执行完一次动作后不需要回报「我现在在哪」。

### 三、为什么用「挪车」补偿而不是改伸出长度

伸出长度固定，末端到转轴的距离就固定为 l，臂只能在一个以转轴为圆心、半径 l 的圆弧上取点。目标点通常不在这条圆弧上，差额只能由车来补：车沿自身 x 移动 d 之后，转轴跟着移动，圆弧随之平移，末端才能落到目标上。

这也是「够不着」的成因：横向距离 |y| 超过 l 时，无论 α 取什么值，末端在 y 方向都到不了目标，只能靠挪车改变转轴的位置——而那已经超出一次解算能给出的答案，所以视觉直接报「横向够不着」。

### 四、无解与告警

| 情况 | 状态字节 bit 0~1 | 电控应做什么 |
|---|---|---|
| 解算成功 | 0 | 按 `shift_x` 与 `arm_yaw` 执行 |
| \|y\| > l，横向够不着 | 1 | 自行决定是否挪车后重新请求 |
| 画面里没测到目标 | 2 | 换观察姿态或调整车的位置后重新请求 |

数学上还有另一支解 `α = 180° − asin(y / l)`，它同样满足方程，但 |α| > 90°，臂会从车身里穿过去，因此不使用。若解出的 |α| 接近 90°，状态字节 bit 2 置起作为告警，提示这一帧的动作余量很小。

### 五、为什么电控在等解算时必须静止

解算的前提是「相机在姿态 (l, α) 下看到的画面」。如果电控在等 `0x0008` 期间动了臂或挪了车，视觉算出的 `shift_x` 与 `arm_yaw` 对应的是一个**已经不存在**的姿态，直接执行会偏。升降同理：靶在画面里的像素直径决定尺度，升降一动尺度就变了，同一帧像素会换成不同的毫米。所以 0x0006 发出后到 done 之前，电控必须保持静止。

同理，视觉在收到同一 seq 的重复 0x0006 时必须**原样重发**上一帧 `0x0008`（逐字节相同），而不是重新解算：重算的结果理论上相同，但重发原帧能保证一致性，也让电控的重复识别更简单。

### 六、执行顺序

先沿自身 x 移动 `shift_x`，再把臂转到 `arm_yaw`。反过来的话，臂先摆到目标方向、车再挪，臂会在移动过程中扫过场上的物料；先挪车时臂保持原姿态，扫过的范围小。

若场地条件不允许先后执行（例如必须边走边转），那是电控自己的规划问题，本协议不做约束——协议只给出「最终应当同时满足这两个量」。

## 1.7 时序与容错

表 1-15 时序参数

| 参数 | 值 | 说明 |
|---|---|---|
| 应答超时 | 100ms | 任务计划未收到 `0x0007` 则重发 |
| 执行超时 | 2000ms | 解算帧未收到 done 则重发。done 在动作执行完才发，必须比纯应答宽松得多 |
| 应答重试上限 | 3 次 | 连续 3 次失败进入安全停止 |
| 位姿上报周期 | 50ms | 三个参考靶可见时发送 `0x0003` |
| 转盘上报周期 | 50ms | 转盘可见时发送 `0x0004` |

表 1-16 臂解算的往返与重发

| 时刻 | 方向 | 帧 | 说明 |
|---|---|---|---|
| 电控停稳后 | 电控→视觉 | `0x0006` 臂状态 | 发出后电控保持静止 |
| 视觉收到后立即 | 视觉→电控 | `0x0008` 解算结果 | 这是对 0x0006 的应答 |
| 电控执行完 | 电控→视觉 | `0x0007` done | `ack_seq` = 0x0008 的 seq |
| 电控等不到 0x0008 | 电控→视觉 | 重发 `0x0006`（seq 不变） | 视觉认出同 seq，原样重发上一帧 `0x0008` |
| 视觉等不到 done | 视觉→电控 | 重发 `0x0008`（seq 不变） | 电控认出同 seq，不再重复执行，只补一次 done（结果字节为 1） |

容错规则：

- 校验失败（`data_length` 越界、CRC8 不符、CRC16 不符）的帧整帧丢弃并计数。
- 丢弃坏帧时**只丢弃 1 字节**，随后从下一个 0xA5 重新查找帧头，不得清空整个接收缓冲。这样粘包场景下一帧损坏不会连带丢弃其后的好帧。
- data 内部出现 0xA5 不会被误判为帧头，由 CRC8 与 CRC16 双重校验排除。
- 数据段长度与表 1-5 不符的帧视为实现不匹配，丢弃并记录，不得使程序崩溃。
- 收到表 1-5 中标注为「不使用」的命令码时静默丢弃并计数。
- 视觉单元在扫码自检不通过时**不发送** `0x0002`，继续扫码；这比发送一份错误的计划让机器人主控开到错误靶位要好。
- **不应答周期测量帧。** 位姿与转盘每 50ms 一帧，若每帧都回应答，链路上有一半是纯应答帧。
- **解算结果必须按 seq 去重。** 同一个 `echo_seq` 只执行一次。视觉因等不到 done 而重发时 seq 不变，电控若不做去重，车会沿同一个 `shift_x` 走两遍——这类错误不产生任何报错，只表现为位置错。

# 附录二：坐标系与角度约定

一、场地坐标系

- 原点为开赛停车位上，机械臂底座中心在地面的投影点。
- x 轴正方向为开赛时的车头方向。
- y 轴正方向为车头方向的左侧。
- 单位一律为 mm。
- 角度为从 x 轴正方向逆时针转过的角度，俯视逆时针为正。

这样定义的结果是机器人主控的开局坐标恒为 (0, 0, 0)，不需要任何初始化换算。

二、车身坐标系

- 原点与轴向同场地坐标系，但**固定在车身上**：原点为机械臂底座中心在地面的投影点，x 轴指向车头，y 轴指向车头左侧，随车平移与旋转。

`0x0004` 转盘模型与内部中间量使用本坐标系。

三、电机坐标系

- 原点在**车身右侧边的中点**，也就是臂的转轴。
- +x 沿车头方向。
- +y 指向车身外侧（俯视图里的画面右方）。
- 车身本体落在 y < 0 一侧，x ∈ [−车长/2, +车长/2]。
- 臂 yaw α 从 +x 量起、向 +y 为正。

`0x0006` 与 `0x0008` 使用本坐标系，解算公式见 1.6 节。

四、角度

- 传输单位统一为 0.1°，即 1.0° 发送为 10。
- 有效取值范围为 −1800~1800，对应 −180.0°~180.0°。
- 发送方应先将角度归一到该区间再打包：

```
value = ((raw + 1800) % 3600) - 1800
```

- 比较两个角度时必须走最短方向，不能用直接相减：270° 会以 −90° 传输，直接相减会得到 360°。

五、量程与饱和

- 坐标字段为 int16，单方向表示范围 −32768~32767 mm，约 ±32.7 m。
- 超出量程时按**饱和钳位**处理，不回绕。接收方无需处理回绕歧义。

六、位姿参考点

`0x0003` 上报的位置是**机械臂底座中心在地面的投影点**，不是相机光轴在地面的投影点。相机光轴到机械臂底座中心的固定偏移计入相机标定参数，赛前测量一次。

这一点必须严格执行：若双方对参考点的理解不一致，上报的位置会整体偏移几十毫米，且不会产生任何报错。

七、位姿的语义

`0x0003` 上报的是视觉单元**独立测算**得到的绝对位姿，不是对机器人主控推算值的修正量。机器人主控收到后应**整体替换**自身的位姿估计，而不是叠加。
